Software Security Maturity Model (I)
What is OWASP SAMM (Software Assurance Maturity Model)?
• OWASP: Open Worldwide Application Security Project
• Open-source framework for software security maturity.
• Helps organizations:
• Evaluate current security practices.
• Build a roadmap for improvement.
• Measure progress over time.
• Help by showing where you are right now & guide to mature & secure practices

Integrating Security into Each Phase of the SDLC (I)
1. Planning & Requirements Phase
• Risk Assessment: Conduct a thorough risk assessment to identify
potential security threats and vulnerabilities.
• Abuse Cases: Provide insights into how attackers will approach the
system's assumptions.
• Security Requirements: Define security and functional requirements
to ensure they are considered immediately.

Integrating Security into Each Phase of the SDLC (II)
2. Design Phase
• Threat Modeling: Utilize threat modeling techniques to identify
potential security risks in the design.
• Secure Design Principles: To mitigate risks, apply secure design
principles, such as least privilege and defense in depth.

Integrating Security into Each Phase of the SDLC (III)
3. Implementation Phase
• Secure Coding Practices: Educate developers on secure coding
practices to prevent common vulnerabilities, such as SQL injection
and cross-site scripting (XSS).

to catch vulnerabilities early.

4. Testing Phase

and dynamic analysis, penetration testing, and vulnerability scanning.

reality and the attacker's mindset. Inside-Out approach

streamline the identification of vulnerabilities.

• How to predict and measure assurance of
security controls.

ISO/IEC 27034—Information Technology—Security
Techniques—Application Security (III)
• Application Security Control (ASC): Specific security function (e.g., input validation)
• use HTTPS, encrypt credit card numbers.
• Application Security Control Library (ASCL): A reusable catalog of ASCs
• company’s library has “payment encryption control,” “session timeout control.”
• Application Security Life Cycle (ASLC): Secure design, development, testing, deployment, maintenance
• Integration of security into every stage of SDLC.
• Application Security Management Process (ASMP): Governance structure ensuring continuous app security
• Managers monitors and ensure developers follow these controls.
• Organizational Normative Framework (ONF): Collection of reusable policies, standards, guidelines, and
resources that help ensure applications are developed and maintained securely.
• company policy says, “all payment apps must comply with PCI DSS.”

9: Security Logging & Monitoring Failures
Not detecting or responding to attacks because logs are missing, weak, or ignored. this category is to help detect,

10: Server-Side Request Forgery (SSRF)
When attackers trick a server into making requests on their behalf, often to internal or protected systems. SSRF flaws
occur whenever a web application is fetching a remote resource without validating the user-supplied URL. It allows an
attacker to coerce the application to send a crafted request to an unexpected destination, even when protected by a
firewall, VPN, or another type of network access control list (ACL).

CWE: Common Weakness Enumeration
• What is CWE?
• It is a catalog (list) of common
software coding mistakes
(weaknesses).
• Published and maintained by MITRE
(a nonprofit that manages security
standards like CVE too).
• Each weakness is given a unique ID
number (e.g., CWE-20: Improper
Input Validation).
• Why CWE matters?
• Helps developers: know what
coding errors to avoid.
• Helps testers/security teams: check
if software has these known flaws.
• Helps organizations: set coding
standards and measure security
maturity.

CWE: Common Weakness Enumeration
The software does not check or restrict input properly, which may allow unexpected or dangerous data.
1. CWE-20: Improper Input Validation
2. CWE-74: Injection
User input is not handled safely, allowing malicious code or commands to be executed.
The program copies data without checking size limits, causing memory corruption.
3. CWE-120: Buffer Overflow
4. CWE-119: Memory Bound Error
The software allows operations outside the allocated memory, leading to crashes or exploits.
5. CWE-384: Session Fixation
The system reuses or accepts an attacker’s session ID, letting them hijack sessions.
